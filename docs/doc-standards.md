# 协作文档的写法约定

> 这份文件管的是**文档本身**，不管代码。改任何 md 之前先读这里。
> `pnpm lint:docs` 会按以下规则校验。

## 为什么要有这份文件

`AGENTS.md` 曾经 500 行、2082 个词，里面有 42 处「禁止 / 必须 / 不要 / 一律 / 硬规则」。
它确实拦住了很多真实的坑，但代价是：**读它的人（或 AI）很容易把「通过校验」
当成目标，而不是「把事情做对」。**

真实的失败长这样：一个任务要求「逐项对齐 Svelte 组件的每个元素」，
但文档里的验收标准全是「跑通 `pnpm lint:*`」。于是我先让检查变绿、截图看着像，
就宣布完成——**这不算撒谎，是标准被文档调低了。**

所以文档要改的不是「少写」，而是**写对优先级**：

1. 先把事做对，再用校验兜底
2. 校验能证明的，才写成硬规则
3. 校验证明不了的（视觉、体验、设计意图），要写成**验收问题**让人回答

---

## 三条规矩

### 1. 硬规则只留给「能自动判定」的事

「禁止引入 ESLint」能判定（看依赖）。「所有 UI 文案走 `t()`」能判定（lint:i18n）。
**「保持设计一致」不能判定**——它必须写成验收问题，不能写成「必须」。

判断方法：如果这条规则写错时 `pnpm lint:*` 不会变红，它就不该用「必须」的口气。

### 2. 验收标准必须包含「人看一眼才能回答」的问题

每个会改变外观/交互的任务，交付前要能回答：

- 和现有实现相比，**多了什么**？
- **少了什么**？
- 哪些地方换成了更省事的实现（通用控件替自绘、emoji 替图标）？

这三问写进 `AGENTS.md` 的「交付前自检」，比任何 lint 都管用——
它们正是我第一次交付时漏掉的东西。

### 3. 文档长度有预算，超出就拆

| 文件 | 上限 | 定位 |
| --- | --- | --- |
| `AGENTS.md` | 260 行 | 索引 + 不可违反的硬规则 + 交付自检 |
| `CLAUDE.md` | 260 行 | 同上，英文版 |
| `docs/*.md` | 不限 | 细节都放这里，正文按需查阅 |

**判断该放哪**：写之前问「不读这条会不会改错代码」。
会 → `AGENTS.md`；不会但排查时要查 → `docs/`。

`AGENTS.md` 里每条超过 5 行的说明，都应该是一个指向 `docs/` 的链接。

## 中英同步

`AGENTS.md` 与 `CLAUDE.md` 是同一份知识的两个语言版本。

- **不用逐字对应**。中英表达习惯不同，强行对齐会让两边都别扭
- **但章节结构必须一致**：`##` 级标题数量与顺序相同
- `pnpm lint:docs` 校验的正是结构，不是措辞

> 旧规则是「改其一时必须同步另一份」，但校验的是**文件名集合**，
> 于是两边为了通过检查会塞进同样的文件名，措辞却各自漂移。
> 改成校验章节结构后，至少能保证「同一件事在两边都有一节」。

---

## 校验什么

`scripts/lint-docs.mjs` 只校验能客观判定的事实：

1. 文档里以反引号包裹的仓库路径**真实存在**
2. `AGENTS.md` 与 `CLAUDE.md` 的 `##` 标题**数量一致**
3. 提到的 `.github/workflows/*.yml` **真实存在**
4. 关键数字与代码常量一致（如 `rt.DetectTimeout` ↔「80 秒」）

**不校验**措辞、排版、段落顺序。那些强行 diff 只会产生噪音，让人想关掉检查。
