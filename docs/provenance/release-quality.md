## 1. 迁移期间不能破的东西

这些是**存量用户已经在依赖**的承诺。迁移的任何一个 PR 都不许碰：

| 承诺 | 具体内容 | 破了会怎样 | 守护机制 |
| --- | --- | --- | --- |
| 产物命名 | `DownVid-Setup-*`、`DownVid-Portable-*`、`DownVid-<arch>-Mac-*`、`DownVid-x86_64-Linux-*` | **所有老用户无法自动更新** | `pnpm lint:ipc` 校验 `artifactName` |
| 更新清单 | `latest.yml` / `latest-mac.yml` / `latest-linux*.yml` 的名字与结构 | 同上 | `scripts/verify-release.mjs` + `test:updater` |
| 仓库坐标 | `yxxbc/downvid` | 更新检查 404，用户永远停在旧版 | `shared/app.ts` 为唯一来源，`lint:ipc` / `lint:website` 静态比对 |
| 设置字段 | 13 个字段，只增不删 | 老用户设置静默失效（MAJOR） | `test:settings:migration` 含「不许绕过入口」静态扫描 |
| 数据目录 | `userData/` 桌面、`./data/{downloads,userdata}` 容器 | 用户数据「消失」 | 迁移计划 §4 |
| IPC 通道 | 39 个通道名与 payload 形状 | 界面功能静默消失 | `lint:ipc` + `tests/ipc-payload.test.ts` |
| 容器 env 变量 | `DOWNVID_*` 一组 | 用户的 compose 文件失效 | 迁移计划 §4 |

**硬规则**：本迁移计划不含任何 MAJOR 变更（定义见 `docs/release.md`「版本语义」）。
如果某个 PR 不得不破坏一条，它必须单独发布、单独写迁移说明、并在 CHANGELOG 里标 **BREAKING**。

## 2. 不只测开发环境：打包产物验证

### 2.1 现状

已有 `pnpm test:package`（校验 `--dir` 打包产物的内容）与 `pnpm test:runtime:windows`
（Windows 原生 exe 集成回归）。**缺**的是「打包产物能不能真的完成一次下载」这一条端到端。

### 2.2 R1 打包产物端到端冒烟（新增）

对每个平台的**实际产物**（不是 `pnpm dev`）跑一条最小链路：

1. 启动应用，等 `/healthz` 等价物或窗口就绪（桌面：日志出现主进程 ready）。
2. 触发依赖探测 → 断言三个依赖都解析到（系统或托管）。
3. 对**本地 HTTP 服务**提供的固定视频文件做一次解析 + 下载（不依赖外网，避免 CI 抖动）。
4. 断言文件落盘、大小与 SHA-256 与夹具一致。
5. 断言历史记录被写入。

**为什么用本地夹具**：`scripts/test-download-integration.mjs` 已经是这个模式；
把它扩展到「打包产物」即可。外网站点在 CI 里会因为改版、限流、地区差异随机失败，
那种失败会训练人忽略红灯。

**验收**：三个平台各跑通一次；失败信息能指出是哪一步（启动 / 探测 / 解析 / 下载 / 落盘）。

### 2.3 发布前人工核对清单

自动化拦不住的部分，写进 `docs/release.md` 的发布步骤（已有条目保持，这里只列与本次架构相关的）：

- [ ] 打包后**手动**跑一次真实站点下载（抖音 / 快手 / YouTube / B 站各一条），确认解析分支真的走通了。
      （AGENTS.md 明确提醒：解析失败会被空 `catch` 吞掉，最终落到 yt-dlp —— 调试时哪个分支运行了是不可见的）
- [ ] 依赖页三个依赖的版本号显示正确（不是「未找到」）
- [ ] 暂停 → 继续 → 完成，文件大小单调增长（aria2 三级进程树那个坑）
- [ ] 更新检查能返回版本（换一次更新源再试一次）
- [ ] 容器：`docker compose up -d` → 浏览器完整走一遍 → `docker compose down` → 再 `up`，数据还在

## 3. 移动端验收（真机，不是模拟器截图）

按 issue §「四」：**在真实设备或适当的模拟环境中验证移动端布局和选定的交付方式**。

| 项目 | 通过标准 |
| --- | --- |
| 屏幕 | iPhone SE（375×667，最小的现代机）与一台 Android（≥ 393×851）各一台 |
| 输入 | 中文输入法下粘贴长链接不被截断；软键盘弹出时下载按钮不被遮挡 |
| 队列 | 3 个任务同时跑时，队列区可滚动、可单独暂停 |
| 触摸 | 所有可点元素 ≥ 44×44 px；无需要 hover 才能发现的操作 |
| 横竖屏 | 旋转后布局不破（不出现横向滚动条） |
| PWA | 可添加到主屏幕；二次打开不白屏、字体（492 KB woff2）不闪烁 |
| 弱网 | 限速到 3G 后，进度条不卡死、暂停按钮仍可点 |

**已知现状**（审计 §6.3）：`src/` 断点类 1 处、`w-[65%]`/`w-[45%]` 写死 → **当前不满足**。
这是 [迁移计划 M1](./migration-plan.md#m1-响应式骨架) 的验收项。

## 4. 容器验收（全新环境）

按 issue §「四」：**在全新环境测试 Docker 镜像，包括持久化存储、配置、访问边界和关闭后重新启动**。

| 项目 | 通过标准 | 备注 |
| --- | --- | --- |
| 全新拉取 | `docker compose pull && up -d` 在空 `./data` 上成功 | 首次启动要解压依赖 |
| 健康检查 | `/healthz` 返回 200 且 body 里带镜像名与版本 | 排障时用户贴这一行就够 |
| 持久化 | 下载完成 → `down` → `up` → 历史与文件都在 | 卷挂载 `./data/{downloads,userdata}` |
| 配置 | 改 `TZ` / `DOWNVID_UPDATE_SOURCE` / 端口后行为跟着变 | 变量名不变是承诺 |
| 访问边界 | 默认 `DOWNVID_WEB_HOST=127.0.0.1`（容器外独立启动）不监听公网；跨源 WebSocket 被拒 | `docker/server/security.ts` |
| 升级路径 | 有新版本时界面给出「`docker compose pull` 并重建」，**不尝试容器内自更新** | 逻辑在 `docker/server/update.ts` |
| 多架构 | `linux/amd64` 与 `linux/arm64` 各跑一遍 | `pnpm lint:docker` + `docker.yml` |
| 依赖可救回 | 故意删掉镜像内依赖 → 界面点「下载」能装回来 | 镜像里依赖下载源与桌面同链路 |

## 5. 署名与归属（保留什么、怎么保留）

### 5.1 必须保留的

| 保留项 | 位置 | 依据 |
| --- | --- | --- |
| 上游版权声明 | `LICENSE` 第 3 行 `Copyright (c) 2024 Videdown (cshuangyy)` | MIT 许可要求保留版权声明 |
| DownVid 自己的声明 | `LICENSE` 第 4 行 | 同上 |
| README 的来源说明 | `README.md` / `README.zh-CN.md` 的 "License and credits" | issue §「四」要求「清楚说明哪些代码由 DownVid 自行开发、哪些仍源自上游」 |
| 第三方依赖致谢 | README 的 credits 列表 | 项目惯例 |

**禁止**：删除、弱化或重写上游版权声明；以「完全自研」表述描述仍含上游代码的部分。
理由不只是合规——issue #74 本身把「厘清来源」写成了目标，自述与实际不符会直接违背该目标。

### 5.2 建议补充的（R2）

1. **`docs/provenance/audit.md` 挂钩 README**：在 "License and credits" 里加一行指向审计文档，
   让任何人能在 30 秒内看到「哪些是上游的、占比多少、怎么复算」。
2. **文件级来源标注（仅对上游成分 ≥50% 的文件）**：在文件头加一行注释，例如
   `// 来源：Videdown 0c620c1 的 electron/main.ts（上游成分 68%，见 docs/provenance/audit.md）`。
   **只对少数文件做**，否则注释噪声会淹没代码。
3. **`CHANGELOG.md` 记录来源变化**：迁移计划 P5 的每个重写 PR，在 `[Unreleased]` 里写
   「X 模块重写，上游成分从 A% 降到 B%」。

### 5.3 许可证方向（待决策，非本文结论）

对齐已关闭的 issue #73 的取向，只记录事实与可讨论方向，不代替决策：

| 组件 | 现状 | 可讨论方向 |
| --- | --- | --- |
| 桌面应用 + 现有代码 | MIT（含上游 2024 声明） | 保持不变。变更需先确认继承代码与外部贡献者的权利 |
| 新增的独立服务端组件（`docker/server/`） | 随仓库 MIT | 评估 AGPL-3.0-only：网络使用即触发源码义务，符合自托管服务端的常见取向 |
| 共享代码（`shared/`、`app/internal/*`） | 随仓库 MIT | 若服务端改为 AGPL，共享代码必须保持兼容许可，否则两端无法同时分发 |
| 品牌素材（名称、Logo、图标） | `TRADEMARKS.md`（已合并 PR #72） | 已经在做「代码许可 ≠ 商标授权」的分离 |

**如果要动许可证，前置条件是本文 §2 的代码来源清单已完备**——否则无法说清「哪些文件可以被重新许可」。
这也是 issue #74 把审计排在第一位的原因。

## 6. 每个发版都要回答的四个问题

发布前对照 issue §「验收标准」逐条自查：

| 问题 | 谁能回答 | 在哪看 |
| --- | --- | --- |
| 哪些代码是 DownVid 自研、哪些仍是上游、哪些是第三方？ | 审计文档 | `docs/provenance/audit.md` §3–§5，`pnpm audit:provenance` 可复算 |
| 桌面发布流程与产物还能用吗？ | CI + 人工清单 | `release.yml` + §2.3 清单 |
| 移动端体验验证过了吗？ | 真机验收 | §3 |
| 容器在全新环境跑通了吗？ | 容器验收 | §4 |

## 7. 不要做的事

- ❌ 为了「看起来是自研」而一次性重写全部代码（issue 明确列为「不在目标范围内」）。
- ❌ 没有明确需求时引入微服务、复杂状态管理层、庞大 UI 依赖。
- ❌ 要求普通桌面用户额外部署 Docker 或服务端。
- ❌ 为宣称自研而重新实现 yt-dlp / ffmpeg / aria2 这类外部工具。
- ❌ 在没有审计依据的前提下调整致谢与归属说明。
- ❌ 在迁移 PR 里顺手改产物名、更新清单结构或删除设置字段（那是 MAJOR）。
